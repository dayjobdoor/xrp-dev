# Changelog

## Unreleased

- **Breaking: `xrp-dev/auth` sign-in is bound to the origin, unique per challenge and optionally single-use.** A challenge is now `<unix ms>.<hex nonce>.<hex hmac>` with a random 128-bit nonce, so two challenges never match, and the HMAC covers the web `origin` as well as the `app`. `createChallenge`, `isFreshChallenge`, `verifyLogin` and `loginWithName` take a required `origin` (the app's own, e.g. `https://app.example`); `loginMessage` and `loginProofTx` take one object `{ app, origin, challenge, name? }` and the signed text is `<app> login\nOrigin: <origin>\n[Name: <name>\n]Challenge: <challenge>`. `login()` passes `location.origin` by default (`origin` outside a browser), builds the text itself and signs the `name` when it gets one, so a relayed signature cannot register another name. New optional `consumeChallenge(nonce, expiresAtMs)` on `verifyLogin` / `loginWithName`: when it returns `false` the answer is the new code `challenge_used`; without it a signed login can be replayed for 5 minutes. Challenges in the old format fail with `challenge_invalid`.
- **Fix (`xrp-dev/auth`)**: `verifyProofTx` checks that the blob has no `Signers` and that its one `SigningPubKey` is the account's own key before it verifies a signature, so a multisigned blob with 32 signers no longer costs about 130 ms. `verifyLogin` answers `invalid_request` for a `proof` over 4096, a `signature` over 160, a `publicKey` over 66 or a `name` over 128 characters.
- **Fix (WebSocket client)**: a timeout fails only the request that timed out. The socket is replaced only when it looks dead: three requests in a row time out and nothing at all (any parsed message, even a late answer) arrives in between. Before, one slow request closed the socket and failed every other request waiting on it with `closed`.
- **Fix (WebSocket client)**: `maxBodyBytes` now applies to WebSocket messages, and `new Client("wss://...", { maxBodyBytes })` passes it on (it was ignored). A message over the cap (default 5 MiB) fails the socket and the requests waiting on it with `ClientError` reason `too_large`.
- **Fix (`autofill`)**: a `ledger_current_index` that would push `LastLedgerSequence` past 2^32-1 is rejected with `no_result`, like any other malformed ledger number, instead of producing a transaction that cannot be encoded. A `LastLedgerSequence` you supply is still never touched or checked against the node.
- **Fix (`submitAndWait`)**: after the submit, an error while looking for the transaction (a dropped connection, a busy node) is retried until `timeoutMs` instead of rejecting the call; the `timeout` carries the last error as `cause`. `timeoutMs` is one deadline for the whole call, each poll and each sleep included. A resubmission answered `tefALREADY` or `tefPAST_SEQ` is no longer `rejected` on the spot: the transaction is looked up by hash and the ledger's result is returned (`tefPAST_SEQ` with no such transaction is still `rejected`).
- **Removed** the unused `bad_signature` `CryptoReason`.
- **Breaking (`xrp-dev/x402`)**: an invoice is bound to the gate that issued it. It is stored with a SHA-256 fingerprint of network, asset, issuer, amount, `payTo` and resource URL, and a payment for an invoice issued by another gate or for another URL gets a fresh 402 (`invoice_not_for_this_resource`) and does not consume the invoice. Before, two gates that share an `InvoiceStore` let an invoice for a cheap route open an expensive one.
- **Breaking (`xrp-dev/x402`)**: `network` is required (it silently defaulted to testnet `xrpl:1`), the `path` option is gone (it compared against the full request path, so a gate mounted through `app.route("/api", ...)` never matched and served the content free; mount the gate with `app.use(path, gate)`), and `settle` and `gate.verifyOnly` are gone (a verify-only delivery never charged and could be replayed). Passing a removed option throws. `chargeOnDelivery` keeps its verify, produce, settle order through an internal handler.
- **Fix (`xrp-dev/x402`)**: only a real CORS preflight (`OPTIONS` with `Origin` and `Access-Control-Request-Method`) skips the gate; any other `OPTIONS` is gated. The gate delivers only when the settlement answer carries a non-empty `transaction` and, if it names one, the gate's network. 402s, gate errors and paid responses carry `Cache-Control: no-store` and `Vary: PAYMENT-SIGNATURE`.
- **Added (`xrp-dev/x402`)**: `InvoiceStore` may implement `claim(id, { ttlSeconds })` (atomic, for example Redis `SET NX EX`) and `release(id)`; the gate uses `claim` so two server processes cannot both deliver one payment. A store shared by several processes must implement it. The `xrp-dev` README has a new x402 section (the facilitator is the trust boundary for ledger checks, `claim` for shared stores, `cors()` first), and the same rules are in the JSDoc of `requirePayment`.
- **Fix (`xrp-dev/mcp`)**: a JSON-RPC batch is limited to 20 messages (a longer one gets one `-32600` reply) and runs at most 4 members at a time; before, 500 `account_info` calls in one batch reached the node as 500 concurrent requests.
- **Release**: `scripts/check-packages.ts` records the SHA-256 of each tarball right after packing, fails if publint, attw or the consumer install changed one, and writes `SHA256SUMS` next to them; the publish job checks it after download and before `npm publish`. `docs/design-document.html` no longer calls the mcp bin Bun-only and names the real build scripts.

## 0.1.0-alpha.5 (2026-11-08)

- **Fix (`xrp-dev/passkey`)**: on Firefox and its derivatives (Zen) the passkey could not be created or used to sign in. Gecko rejects `navigator.credentials.create` and `.get` with `NotAllowedError` while the window is not the active one, and a macOS passkey sheet that has just closed has not given the focus back yet, so the second ceremony in a row (the PRF read after `registerPasskey`, then a signature) was refused. `registerPasskey` and every `PasskeyAdapter` ceremony now wait for the window's focus first (at most 10 s, then the call is made so the browser's own error shows). With focus the call still runs in the same task, so Safari keeps the click's user activation. `focused(call, waitMs?)` is exported from `xrp-dev/passkey` for apps that call WebAuthn themselves.
- **`PasskeyError`**: the "dismissed or timed out" message now ends with the browser's reason, e.g. `the passkey prompt was dismissed or timed out (CredentialsContainer request is not allowed.)`. `NotAllowedError` also covers a browser that refused the call, which the old message hid. `cause` is unchanged.
- **Breaking: `xrp-dev`, `xrp-dev/crypto`, `/address`, `/codec` and `/client` no longer return Effects.** The crypto, address and codec functions are synchronous: they return the value and throw the tagged error (`AddressError`, `CodecError`, `CryptoError`; `instanceof` works). `autofill` and `submit` return Promises, and the clients from `createRpcClient` / `createWsClient` have `request` (and, for WebSocket, `close`) returning Promises that reject with `ClientError`. A custom `RpcClient` can be written with plain `async` functions; a rejection that is not a `ClientError` becomes one with reason `http`, the original message and no `cause`, and a custom client has no timeout or abort from this library (it brings its own). `encode` throws `CodecError` (`bad_length`) for objects nested more than 16 deep (what `decode` accepts) instead of recursing without a limit. `xrp-dev/auth`'s `verifyMessage` and `verifyProofTx` return `string | undefined` instead of an Effect (there is no Effect twin; wrap them with `Effect.sync` if you need one). The Effect API is unchanged and moved to `xrp-dev/effect` (`xrp-dev/effect/crypto`, `/address`, `/codec`, `/client`): replace `from "xrp-dev/codec"` with `from "xrp-dev/effect/codec"` and so on to keep the old behavior. `PasskeyAdapter({ client })`, `xrp-dev/mcp`'s `Deps.client` and the Effect `autofill` / `submit` accept either client, the Promise one of `xrp-dev/client` or the Effect one of `xrp-dev/effect/client`; `toEffectClient` (from `xrp-dev/effect/client`) converts explicitly. MCP tool handlers still return Effects.
- **Breaking: `xrp-dev/wallet` is plain too.** `Wallet.fromEntropy`, `fromSeed`, `fromSecretNumbers`, `sign`, `signMessage`, `toSecretNumbers` and `entropyToSeed` are synchronous: they return the value and throw `WalletError` (`sign` can also throw `CodecError`). `Wallet.fromPrf` and `entropyFromPrf` return Promises, because HKDF is WebCrypto. The implementation is plain functions and imports no `effect` (`xrp-dev/wallet`: 123 KB minified, gzip 38.0); every copy of the key is zeroed in a `finally`, however a call ends. The Effect API is `xrp-dev/effect/wallet` (141 KB, gzip 44.2), a thin adapter over the same functions with the alpha.4 signatures: replace `from "xrp-dev/wallet"` with `from "xrp-dev/effect/wallet"` to keep the old behavior. `WalletError` is a plain `Error` like the others (`_tag`, `reason`, `position`, optional `cause`), no longer a yieldable `Data.TaggedError`. `signingRefusal` and `xrp-dev/passkey` are the same in both.
- **xrpl.js-style client**: `new Client(url)` (a JSON-RPC or `wss://` address, or `"mainnet"` / `"testnet"` / `"devnet"`) with `request`, `autofill`, `submit`, `submitAndWait`, `connect()` and `disconnect()`. `request` takes `(method, params)` or `{ command, ...params }` and resolves to the node's `result`. `submitAndWait(client, blob)` (also a function) submits and waits until the transaction is in a validated ledger, resolving to `{ hash, engine_result, transaction_result, tx }` (`transaction_result` is the validated outcome, `tesSUCCESS` or a `tec…` code); it rejects with `ClientError` reason `rejected` (`tem`, `tef`, `tel`), `expired` (past `LastLedgerSequence`), `timeout` or `aborted`. Every Promise call takes `{ signal }` (reason `aborted`), and `autofill`, `submit`, `submitAndWait` take `{ timeoutMs }`; a custom `RpcClient` receives the signal as `request(method, params, { signal })`. New `ClientError` reasons: `aborted`, `rejected`, `expired`. `toEffectClient` (from `xrp-dev/effect/client`) turns either kind of client into the Effect one.
- **`effect` is a dependency**: it moved from `peerDependencies` to `dependencies` (`^4.0.2`) and is installed with `xrp-dev`. Your package manager shares it with your own copy when your range overlaps `^4.0.2` (depend on `effect@^4`); the Effects from `xrp-dev/effect` (including `xrp-dev/effect/wallet`) and `xrp-dev/mcp` then run on your runtime. The error classes are plain classes of `xrp-dev`, so `instanceof` and `catchTag` do not depend on how many copies of `effect` are installed. An app that uses only the plain entries need not list `effect`.
- **Hashing is synchronous**: `sha256`, `sha512` and `sha512Half` use `@noble/hashes` instead of `crypto.subtle`, so they no longer suspend, and code that hashes works with `Effect.runSync` in `xrp-dev/effect`. Hashing, addresses, the codec and signing no longer need a secure context in the browser; only `xrp-dev/auth`'s HMAC (the server half) and the wallet's HKDF still use `crypto.subtle`. They accept only a `Uint8Array` and throw `TypeError` for anything else (`crypto.subtle` copied its input, so a `number[]` or `ArrayBuffer` worked, and a string or `DataView` was silently hashed as empty). Output for valid input is unchanged (the codec, ripple-binary-codec and Wycheproof differential tests pass).
- **The synchronous entries no longer load `effect`**: `crypto`, `address`, `codec`, `auth` and `wallet` are plain TypeScript, and `xrp-dev/effect/{crypto,address,codec,wallet}` are thin adapters over the same functions that fail with the same error instances. (`xrp-dev/effect/client` is the I/O implementation, written in Effect, and `xrp-dev/client` wraps it with `Effect.runPromise`.) Minified bundle of the entry (`bun build --target=browser --minify`, gzip -9), alpha.4 → now: `codec` 138 KB (gzip 42.8) → 117 KB (35.9), `crypto` 80 KB (29.6) → 61 KB (23.3), `address` 82 KB (30.3) → 62 KB (23.6), `auth` 151 KB (47.3) → 121 KB (37.1), `client` 118 KB (35.5) → 114 KB (33.7: it still carries `effect`, and `submitAndWait` decodes the blob to read its `LastLedgerSequence`, but it no longer carries the curves it never used; 91 KB (25.8) before `submitAndWait`), `xrp-dev` (crypto, address, codec, client) 148 KB (46.2) → 167 KB (52.7). Import the subpaths for the small bundle.
- **Errors are plain `Error`s**: `CryptoError`, `AddressError`, `CodecError` and `ClientError` no longer extend Effect's `Data.TaggedError`. `_tag`, `reason` (and `field` on `CodecError`) are unchanged, so `Effect.fail`, `Effect.catchTag` and `instanceof` keep working, and a `cause` can now be attached. They are no longer yieldable: `yield* new AddressError(...)` inside `Effect.gen` must become `yield* Effect.fail(new AddressError(...))`. `message` is no longer an own enumerable property, so `JSON.stringify(error)` no longer includes it (read `error.message`). Their reason types are exported (`AddressReason`, ...). `WalletError` (`xrp-dev/wallet`) follows the same change.
- **Fix (`autofill`, `submit`)**: an answer that is not an object (a node or a hand-written client returning `null`, a string, ...) now rejects with `ClientError` reason `no_result` instead of a `TypeError`, and `submit` rejects an answer without a string `engine_result` (it used to resolve with something typed `SubmitResult` that was not one; a missing `engine_result_message` is filled with `""`). Same for the Effect versions in `xrp-dev/effect/client`.
- **Types**: `loginProofTx` returns the exact shape it builds (`LoginProofTx`, exported from `xrp-dev/auth`: an `AccountSet` with `Sequence` 0, `Fee` "0", `LastLedgerSequence` and one memo, and no `SigningPubKey`) instead of `TxJson`, so it goes to a wallet adapter's `sign` without a cast; it is still assignable to `TxJson`. The Effect `RpcClient.request` takes an optional third `options` argument (`{ signal }`, which an Effect client may ignore); an existing client with two parameters still fits.
- **`xrp-dev/effect`** also exports `lift`, `liftAsync` and `liftTotal`, the adapters it uses itself: `lift(CodecError)(f)` turns a function that throws that class (or `lift(A, B)`: either) into one returning an `Effect` that fails with it; any other throw is a defect.

## 0.1.0-alpha.4 (2026-10-22)

- **`xrp-dev/xahau`**: transaction types for the Xahau-only transactions (`SetHook`, `Import`, `Invoke`, `ClaimReward`, `SetRemarks`, `Cron`, `CronSet`, `Remit`, `URIToken*`, plus `Hook`, `Remark`, `XahauAmount`, union `XahauTransaction`), after xahau.js. Types only, `Flags` are numbers, each is assignable to `TxJson`.
- **Wallet**: `signingRefusal` refuses an `Import` whose XPOP's inner XRPL transaction is `SetRegularKey` or `SignerListSet` (Xahau carries the keying over to the account; an empty `SetRegularKey` without a signer list disables the master key), and an `Import` whose XPOP it cannot read. An inner `AccountSet` (the standard burn-to-mint transaction) and other inner transactions stay signable. It reads the inner type from the blob's first field, so no full decode runs.
- **CI**: a re-run or queued run whose `plan` read a stale `npm view` (registry lag right after another run published) no longer fails the publish job: an exact-version `cannot publish over the previously published versions` 403 counts as already published, and `Tag and release` is skipped when the tag exists.

## 0.1.0-alpha.3 (2026-10-21)

- **`xrp-dev/name`**: one unique, immutable name per account, bound at sign-up, for every app. `xrp-dev/name` (browser-safe, imports no `effect`): rules (`parseName`, `RESERVED_NAMES`: lower case `[a-z0-9_]`, 3-20, no leading or trailing `_`, xrpst's reserved words plus `vocab` and route-like words), `NameError` (a plain `Error` with `_tag`, `code`, `reason`) and the client half (`checkNameAvailability`, `createNameChecker`, `nameErrorFrom`, `registerWithName`, which validates locally and calls `register(name)` synchronously so Safari keeps the user activation; a name taken meanwhile comes back as `name_taken` from `login()`, leaving an accepted orphan passkey). `xrp-dev/name/server`: `registerPasskeyAccount`, `claimName`, `loginWithName`, `checkNameAvailable`, `nameAvailabilityHandler` and the Effect-based `validateName` over a `NameStore` of `findByAccount`, `findByName` and `create`; the database's UNIQUE error becomes `name_taken` and a same-account race returns the existing row. Wire codes `name_required` 428, `name_invalid` 400 (+ `reason`), `name_taken` 409 match xrpst. `login()` now throws a `LoginError` (an `Error` with `status`, `code`, `reason`).
- **Fix**: `loginProofTx` set `LastLedgerSequence: 1` and `SigningPubKey: ""`, so `login()` with Xaman (xrpl-connect's `XamanAdapter`) never reached the wallet: its `sign()` refuses a `LastLedgerSequence` below 32570 (small values read as relative offsets), and an empty `SigningPubKey` turns the payload into a multisign request. The proof now carries `LastLedgerSequence: 4294967295`, the largest value `sign()` accepts, so Xaman never sees it as expired and has no reason to raise it (xrpl-connect rejects a raise of more than 50 ledgers). `SigningPubKey` is left to the signer. The proof stays unappliable (`Sequence` 0, `Fee` 0), and `verifyProofTx` is unchanged. Not yet confirmed against the Xaman app itself.
- **Fix (x402)**: `chargeOnDelivery` treated any `next()` from the gate as "payment verified", so an `OPTIONS` request or a path outside `path` carrying any `PAYMENT-SIGNATURE` delivered `produce()` output unpaid; it now requires a real facilitator verification. With `x402SecurePolicyId` set the gate now refuses to settle when `verify` returned no `decisionToken`. A second request for an invoice that is still being processed gets `409 payment_in_progress` (per process; `chargeOnDelivery` holds the invoice across verify, `produce` and settle, so `produce` runs once). The default in-memory invoice store is capped at 10,000 entries (expired first, then oldest) instead of growing with every unauthenticated 402.
- **Wallet**: `signingRefusal` also refuses `SetHook` (Xahau: installs code that can block or emit transactions for the account). `Import` is still signable.
- **CI**: the publish job no longer runs `bun run check` (it fetches unlocked `bunx` tools beside the OIDC token; `verify` runs it on the same commit) and installs `npm@11.21.1` exactly. It also no longer rebuilds: `verify` uploads the tarball it checked and `publish` publishes that file, then creates a GitHub Release from this changelog. A `node-floor` job runs the consumer smoke test on Node 20.19. Bun is pinned to 1.4.x.
- **Package**: the tarball now includes `CHANGELOG.md`.

## 0.1.0-alpha.2 (2026-10-19)

- **Fix**: `autofill` with `definitions` probed `fee` with a blob lacking `Sequence` and `Fee`, which xahaud answers with `invalidTransaction`; every `PasskeyAdapter` send on Xahau without a preset `Fee` failed. The probe now carries `Sequence: 0` and `Fee: "0"` placeholders.

- **`xrp-dev/auth`**: wallet sign-in for apps. `createChallenge` / `isFreshChallenge` (stateless HMAC challenge bound to the app name, 5 min, constant-time compare), `loginMessage`, `verifyMessage`, `loginProofTx` / `verifyProofTx` (an unappliable `AccountSet` memo transaction for wallets that cannot sign messages), `verifyLogin` (server: challenge + signature or proof in one call, returns an address or a failure code) and `login(adapter, { app })` (browser: challenge, sign, post, session cookie).
- **`xrp-dev/xahau`**: `XAHAU_DEFINITIONS` and `XAHAU_PROTOCOL`, a `server_definitions` snapshot of Xahau (hooks, Import, URIToken, ...). Not re-exported from `.`, so the extra JSON loads only for those who import it.
- **Codec tables are a parameter**: `makeDefinitions(raw)`, `XRPL_DEFINITIONS`, and an optional last `defs` argument on `encode`, `decode`, `encodeForSigning`, `encodeForMultisigning`, `verifyTransaction`, `signerMatchesAccount`. `Wallet.sign(tx, { definitions })` and `PasskeyAdapter({ definitions })` use it. `scripts/definitions.ts` takes `--out <name>`.
- **`NETWORK_PRESETS`** (`xrp-dev/client`): `xrpl:mainnet|testnet|devnet` and `xahau:mainnet|testnet` with `networkId`, `rpc`, `ws`, `explorer` and `faucet`. `PUBLIC_RPC_URLS` is built from it.
- **`autofill` options** `networkId` (adds `NetworkID` when above 1024) and `definitions` (asks `fee` for this transaction's `tx_blob` and uses `base_fee`, which includes hook fees). `PasskeyAdapter` takes `networkId` and passes both.

## 0.1.0-alpha.0 (2026-10-16)

First release as `xrp-dev` (one npm package; `wallet`, `passkey`, `mcp` and `x402` are subpaths).

- **Entry points**: `xrp-dev` (crypto, address, codec, client; holds no keys), `xrp-dev/wallet`, `xrp-dev/passkey`, `xrp-dev/mcp` (bin `xrp-dev-mcp`), `xrp-dev/x402` (Hono gate for x402 v2 exact payments; optional `hono` peer).
- **Passkey derivation can be set per app**: `entropyFromPrf` and `Wallet.fromPrf` take `{ salt, info }`, `registerPasskey` and `PasskeyAdapter` take `derivation: { prfInput, salt, info }`. The default stays `xrp-dev/prf/v1`. A test pins another app's frozen vectors (ed25519 and secp256k1) so such an app keeps its addresses. **Breaking** against earlier unpublished builds: `entropyFromPrf(prf, opts)` replaces `entropyFromPrf(prf, salt)`.
- **`algorithm` option** on `PasskeyAdapter` and `registerPasskey` (`"secp256k1"` default, `"ed25519"`).
- **`registerPasskey` leaves no orphan passkey** and now returns `{ credentialId, account }` (it throws instead of returning `prf: false`): refuses a browser that reports no PRF support before creating anything, asks an `enabled`-only authenticator once more with the new credential, and reports a passkey without PRF to the OS (`signalUnknownCredential`).
- **Page-load restore without a prompt**: `PasskeyAdapter.serializeReconnectOptions()` lets xrpl-connect's `WalletManager.reconnect()` restore the account from public data (`address`, `publicKey`, `credentialId`, `algorithm`). Incomplete data or another algorithm fails instead of prompting; every signature still re-derives the key and refuses a different address.
