xrp-dev // Web Standard XRPL SDK

An XRPL SDK with no Node.js dependency, developed as a monorepo in this repository (codemode). Besides the library itself, the same repository provides the entry points used from AI (Code Mode connector, MCP, Skills) and a browser app that signs with a Passkey. This document covers the API, dependencies, and tests of each package. Published as one npm package, xrp-dev (xrp-dev/wallet, xrp-dev/passkey, xrp-dev/mcp). The three-name layout below is the source layout, not three publishes.

04Library packages

Common policy

  • Use Effect 4 (D3). Fallible operations return Effect.Effect<A, E>, and errors are per-domain Data.TaggedErrors (CodecError, CryptoError, AddressError, ClientError, WalletError). They are subdivided by reason (e.g. "unknown_field"). Pure functions that cannot fail (such as bytesToHex) return values.
  • Hashing uses crypto.subtle (async), so anything that includes hashing (signing, address derivation, transaction hashing) is async inside Effect. The codec itself does not use hashing.
  • Call Effect.runPromise only at boundaries that need a Promise (the xrpl-connect adapter, MCP handlers).
  • Byte input and output use Uint8Array, and hex is an uppercase string. Buffer is not used.
  • Objects that hold key material do not expose their contents through toJSON() or toString(). destroy() fills the bytes with 0.

Caveats when deriving keys from a PRF.
  • The key exists temporarily in JavaScript memory.
  • It cannot be used with authenticators or browsers that do not support PRF.
  • If the same Passkey is lost, the same address can never be restored. Therefore a Secret Numbers backup is shown at creation (an app requirement).
  • The HKDF salt and info are fixed to "xrp-dev/prf/v1", with the version included in the name.
Signing refusal (signingRefusal). On 2026-10-11 xrp-dev-wallet exports signingRefusal. It refuses to sign Batch, SetRegularKey, SignerListSet, DelegateSet, and AccountSet with asfDisableMaster. It is enforced in PasskeyAdapter.sign / signAndSubmit, and the app's confirmation screen uses the same function.

xrp-dev-wallet/passkey — xrpl-connect adapter

Until 2026-10-11 this was a separate package, @xrp-dev/passkey; it is now a subpath of xrp-dev-wallet (D7).

WalletAdapter of xrpl-connect 1.0.0 (quoted from the actual type definitions):

interface WalletAdapter {
  readonly id: WalletIdentifier; readonly name: string; readonly icon?: string; readonly url?: string;
  readonly capabilities?: WalletCapabilities;
  isAvailable(): Promise<boolean>;
  connect(options?: ConnectOptions): Promise<AccountInfo>;      // { address, publicKey?, network }
  disconnect(): Promise<void>;
  getAccount(): Promise<AccountInfo | null>;
  getNetwork(): Promise<NetworkInfo>;
  sign(transaction: Transaction): Promise<SignedTransaction>;     // { hash, tx_blob?, … }
  signAndSubmit(transaction: Transaction): Promise<SubmittedTransaction>;
  signMessage(message: string | Uint8Array): Promise<SignedMessage>;
  on?(event: WalletAdapterEvent, cb: (data: unknown) => void): void;
  off?(event: WalletAdapterEvent, cb: (data: unknown) => void): void;
}
  • No dependency on xrpl-connect. xrpl-connect has xrpl (xrpl.js) as a peer dependency, and its dependencies also include @types/node. Even import type pulls @types/node into the types, so only the needed types (such as AccountInfo) are declared inside the package, and satisfies WalletAdapter is checked in a test (devDependency) (K01).
  • Implementation of each method:
    • connect(): calls navigator.credentials.get() with PRF and creates the key with Wallet.fromPrf.
    • sign(): calls Wallet.sign.
    • signAndSubmit(): submits with submit from xrp-dev/client. The destination is a public node directly from the browser, not via this repository's server. The Effect is converted to a Promise with Effect.runPromise and returned.
    • disconnect(): calls Wallet.destroy().
  • Prior art: xrpl-connect already has an adapter for GHOSTSIG, a hosted Passkey wallet. This design differs in that it creates the key on the device from the PRF, without going through a host.
  • Support for XLS-83d: ledger-native Passkey signing will be supported after the specification becomes Final. An internal Signer interface is provided so that the signing method can be swapped.

Do not create any path through which the model sees keys. No entry point has a tool that takes a seed, private key, entropy, or PRF output as an argument or return value. Signing happens only on the user's device (a browser operated by a person, or the user's own code). The server receives only a signed tx_blob, and submission is limited to one authenticated submit.

codemode/apps/agent/src/xrp-connector.ts — Code Mode connector

  • XrpConnector extends CodemodeConnector (the base class of @cloudflare/codemode 0.5.3). Inside the sandbox it can be called like xrp.decode(...). The name codemode is reserved by the SDK.
  • Tools: encode, decode, hash_transaction, derive_address (from a public key), classic_to_x_address, x_address_to_classic, is_valid_address, prepare_payment, prepare_trust_set, prepare_offer_create. prepare_* runs autofill through the existing XRPL Service Binding and returns only { tx_json } (signingData / signingHash were removed on 2026-10-11: they were computed without SigningPubKey, so they did not match what the signer actually signs). It contains no signature. Once the signer inserts the key, the signing target is determined.
  • The connector is built from the MCP registry and validates arguments. Argument names are the same as MCP (encode{tx_json}, decode{tx_blob}, hash_transaction{tx_blob}). serviceBindingClient in codemode/apps/agent/src/binding.ts consolidates the Service Binding's RpcClient into one.
  • Pure-computation tools use replay: "reexecute", so that results are not kept in the durable log. submit is not provided: Pi tools have no approval mechanism, and if Code Mode stops waiting for approval (paused) there is no path to resume it.
  • There is also a way to run the computation directly inside the sandbox. The modules of DynamicWorkerExecutor (Record<specifier, source>) are passed as-is to the Worker Loader, so a bundle can be placed there (confirmed in the 0.5.3 source). User code is wrapped inside a function, so only dynamic import() appears to be usable. Execution on workerd has not been verified needs verification
  • The existing agent can pick it up just by setting connectors: [XrplConnector, XrpConnector]. It also becomes usable from the MCP execute tool.

xrp-dev-mcp — MCP

  • Tool definitions (name, description, JSON Schema, annotations, handler) are gathered into one registry. All tools except submit have readOnlyHint: true. There are two transports:
    • Remote: add the tools to the existing agent POST /mcp (hand-written JSON-RPC).
    • Local: start a stdio server with bun packages/mcp/bin/mcp.ts --network testnet (run from the repo root; after npm publication, bunx xrp-dev-mcp). Bun-only.
  • Tools: the same set as Code Mode, plus read tools such as account_info and tx. Remote uses the Service Binding; local uses a public node.
  • The MCP SDK is not used. As in the current agent, only four methods are implemented (initialize, tools/list, tools/call, notifications/*).

Submission (D1: authenticated)

Server-side submission is limited to one agent MCP tool, submit. It submits only when all of the following conditions are met.

  1. Caller authentication: the agent's bearer token (the existing requireToken). Local stdio does not expose submit.
  2. Signer authentication: it accepts only a signed tx_blob. It decodes it, verifies TxnSignature (or each signature in Signers) with SigningPubKey, and confirms that the account of that public key matches Account (RegularKey is Phase 2, confirmed via account_info). The signature is made on the user's device with a Passkey or similar, and the server holds no keys.
  3. Per-call approval: the tool carries destructiveHint: true, relying on confirmation on the MCP client side (such as Claude Code's permission prompt).
  4. Destination: the agent submits directly to a public node. It does not go through the xrpl Worker (which stays read-only). The network is chosen by an argument, and the default is testnet.
  5. Logging: log the hash of the submitted transaction, the account, the network, and rippled's engine_result. The full blob is not logged.

"Authenticated" was interpreted as the combination of 1–3 above. If the interpretation is wrong, fix this section and AGENTS.md.

Signing

  • secp256k1: signs sha512Half(STX\0 ‖ serialization). It is a deterministic RFC 6979 signature, normalized to low-S and DER-encoded.
  • ed25519: signs STX\0 ‖ serialization itself, not a hash. The first-edition description "sign the first 32 bytes" does not apply to ed25519.
  • secp256k1 key derivation:
    1. Root private key: compute sha512Half of seed ‖ seq (32 bits, from 0), and use the first value that is nonzero and less than the curve order.
    2. Intermediate: select sha512Half of the root's compressed public key ‖ accountIndex(0) ‖ subseq under the same condition.
    3. Private key = (root + intermediate) mod n.

Codec

  • Definitions: the result of rippled's server_definitions is committed as definitions.json. Updates are done by script, and tests run offline.
  • Field order: ascending by (type code, field code). The Field ID is 1 byte if both type and field are below 16, 2 bytes if one of them is 16 or more, and 3 bytes if both are 16 or more.
  • Variable-length length prefix:
    • 0–192 is 1 byte
    • 193–12,480 is 2 bytes
    • 12,481–918,744 is 3 bytes
    • Anything beyond that is an error
  • Amounts:
    • XRP is 64 bits (leading bit 0, the next bit is the sign), with an upper limit of 1017 drops.
    • An issued currency is: leading bit 1, sign, exponent (8 bits, offset by +97), and a 54-bit mantissa (normalized to 1015–1016−1). Zero is 0x8000000000000000.
    • It is followed by a 20-byte currency and a 20-byte issuer.
    • An MPT amount is 33 bytes. The first byte is 0x60 (positive sign and the MPT flag), followed by an 8-byte value (0–263−1) and a 24-byte MPT issuance ID. In JSON it is { mpt_issuance_id, value }.
  • Number and Int32:
    • Number is 12 bytes: a signed 64-bit mantissa followed by a signed 32-bit exponent, both big-endian. The mantissa is normalized to 1018–263−1, and digits that overflow are rounded at the last digit. Zero is mantissa 0 and exponent −231. Normalization and conversion to string are the same as ripple-binary-codec (the only difference is that decode places the decimal point as the value is, when the mantissa is below 1017).
    • Int32 is a signed 32-bit big-endian. In JSON it is a number.
  • Issue: XRP is only 20 zero bytes. An issued currency is a 20-byte currency and a 20-byte issuer. MPT is a 20-byte issuer, 00…01 (20 bytes), and a 4-byte sequence (little-endian). In JSON it is { mpt_issuance_id } (4 bytes of the sequence in big-endian, and the issuer).
  • Currency codes:
    • A 3-character code is placed at bytes 12–14 of the 20 bytes.
    • Using "XRP" as the code of an issued currency is an error.
    • A 40-digit hex is handled as is.
  • Extension point: XLS-83d fields can be handled just by adding them to definitions.json.

  • noble targets algorithmic constant time (fixed operation sequence, scalar blinding) and says itself that no JavaScript library can guarantee constant-timeness (JIT, GC). 11Lessons from xrpl.js / xrpl-connect

ItemExisting situationResponse in this design
Runtime switchingxrpl.js resolves Node and the browser conditionally with @xrplf/isomorphic, and polyfills tend to bloat on workerdRemove conditional branches and assume only Web Standard (P01, P02)
Byte arraysAssumes BufferUse only Uint8Array / DataView
WebSocketUses ws on NodeThe global WebSocket. Make it replaceable for tests
BundlersThe interpretation of main / module differs per bundlerEmit only types and import in exports (ESM only)
Adapterxrpl-connect declares capabilities with WalletAdapter and capabilitiesImplement the same type and keep Passkey-specific handling inside the adapter. xrpl-connect is used only as a type
Dependenciesxrpl-connect has xrpl.js as a peer dependencyNo runtime dependency. Only the types of /passkey refer to xrpl-connect and xrpl as optional peers. Named Flags (objects) are refused, since converting them requires xrpl.js (K03, K05)
